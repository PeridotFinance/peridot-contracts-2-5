# PharaohDlmmVault (W2): deviations, decisions and notes for W4 / W5 / W9

The interface `src/IPharaohDlmmVault.sol` is implemented unchanged (the contract declares `is IPharaohDlmmVault`; no signature changed). Everything below is either additive (extra errors, events, getters) or a decision where the spec/interface was silent. Claims are labelled MEASURED / DERIVED / ESTIMATED.

## 1. Main-thread decisions applied (coordinator, 15 Nov)
1. `initialize` sets the rebalancer; `setRebalancer` is for rotation. Rebalancer-gated calls accept ONLY the rebalancer (not the owner, unlike R3's `onlyRebalancer`); `harvestRewards` accepts rebalancer or owner (error `NotRebalancer`).
2. `openBand` is rebalancer-only and only when NO band exists (`BandExists()` otherwise). Deposits made while a band exists (or before the first openBand) sit idle, count in NAV at par (USDC) and are folded in at the next `openBand` / `rebalance`. R3 conflict: R3 deployed every deposit into the position inside `deposit` (R2 swap path); here `deposit`/`mint` never touch the pair or the router (no sandwich surface, no 111 s forfeiture reset per deposit). Consequence: idle USDC earns nothing until a band is opened or the next exit-triggered rebalance.
3. `initialize` leaves the vault PAUSED (blocks deposit, mint, openBand, rebalance; never exits). The cap 200e6 is set before. The owner (Safe) calls `unpause()` after the read-backs. R3 conflict: none (R3 also ends `initialize` paused).
4. `maxMint = convertToShares(maxDeposit)`; `setDepositCap(0)` allowed (cap 0 = no deposits; R3's "0 = unlimited" is NOT carried over). Documented brake is `pause`.
5. `harvestRewards` forwards the vault's whole PHAR balance to the owner (as R3). Event `PharHarvested(token, amount, totalSupply(), totalAssets)`: `totalAssets` is 0 when a feed is bad (a harvest must not depend on the feeds). R3 conflict: R3's harvest was `onlyOwner` and had xPHAR exit logic (deleted: DLMM pays PHAR only) and a `claimPosition` flag (none here: `claim(vault, bandIds)` always; with no band it still pays what earlier burns settled).
6. Guard bit 16 orientation (coordinator correction): pool price = Y per X from the pair order read at `initialize` (`assetIsX`); oracle ratio = priceX/priceY = feed(X leg) / feed(Y leg). For USDt (X) / USDC (Y): feedPair(USDT/USD) / feedAsset(USDC/USD). Coded this way from the start (no change needed). Pinned by `W2Smoke.t.sol::test_poolOracleDeviationBit` for the X = USDt order only; W4 must add the other order.

## 2. Deviations from the spec text / R3 (the main thread decides)
- **D1 (ACCEPTED) `redeem` / `withdraw` pay what the slice REALISES (redeemer bears the swap cost).** R3 paid `convertToAssets` and made the vault absorb the swap (covered by a 0.5 to 1.5 % valuation haircut). With no haircut here (NAV is the ownership NAV) that would let an exit sandwich (move the pool within `maxRebalanceLossBps`, redeem, reverse) transfer value from the other holders. So: burn the redeemer's pro-rata slice of the bins and of the idle balances, swap the USDt part to USDC through the router with min out = oracle value x (1 - `maxRebalanceLossBps`), pay slice USDC + swap proceeds. Unfavourable consequences: (a) `redeem` can pay slightly less than `previewRedeem` (swap fee 0.0025 to 0.0225 % plus the pool's standing discount, MEASURED about 11 bp median, on the USDt half only), violating ERC-4626's "preview <= actual" in the other direction (preview overstates); (b) `withdraw(assets)` burns `ceil(convertToShares(assets))` shares and pays what the slice realises, i.e. it may pay slightly LESS than `assets` (not ERC-4626 exact-out). Integrators needing exactness should use `redeem` or `redeemInKind`.
- **D2 `totalAssets()` = the ownership NAV (no haircut), reverts `FeedInvalid(1|2)` when a feed is bad/stale.** Hence `previewX`, `convertToX`, `maxWithdraw`, `redeem`, `withdraw` revert in that state (as the spec's section 3 says); `maxDeposit`/`maxMint`/`guardState`/`rebalanceAllowed`/`bandState` never revert. An out-of-band feed answer (bits 4/8) does NOT revert NAV.
- **D3 (ACCEPTED) Validation lives in a second contract.** The vault runtime with inline validation was 28.2 KB (> EIP-170 24,576). `src/PharaohDlmmPairValidator.sol` (stateless, view) is deployed BY THE IMPLEMENTATION'S CONSTRUCTOR (`new`, no constructor argument) and stored as an implementation immutable; `initialize` staticcalls it and bubbles its revert unchanged. Runtime now 23,685 bytes (891 B margin, MEASURED `forge build --sizes`), initcode 27,730. W4 still deploys `new PharaohDlmmVault()` with no argument. A deployment script's gas for the implementation is higher (validator creation inside the constructor). ACCEPTED by the main thread. The validator's address is `CREATE(implementation, nonce 1)` (a contract's first created contract uses nonce 1), so the ceremony read-back can compute it (`cast compute-address <implementation> --nonce 1`); it is a private immutable, so it cannot be read from the implementation, and it needs its own source verification on the explorer.
- **D4 `DEPOSIT_CAP_CEILING`** is an implementation immutable set in the constructor to 200_000_000. `initialize` reverts `CapAboveCeiling(requested, ceiling)` above it.
- **D5 In the exit paths the pair-read helpers use plain `a*b/c` instead of `Math.mulDiv`** (size). Bound (DERIVED from a MEASURED sample): LB shares are about 8e15 per raw unit (pair bin 8388598: totalSupply 2.7e25 for 3.36e9 raw), so a vault capped at 200 USDC holds < 1e27 shares of a bin; the products stay far below 2^256.
- **D6 (RESOLVED by the main thread): `openBand` has NO cap post-check.** The cap is enforced where assets enter (deposit, mint, maxDeposit, maxMint). Reason: with NAV exactly at the cap, a favourable swap lifts NAV above it and would have made `openBand` revert (reproduced before the change with feedPair 1.001). Pinned by `test_capExactThenOneWeiRevertsAndOpenBandSurvivesFavourableSwap`. `rebalance` has no cap check either. Consequence: NAV may exceed the cap through gains, fees or favourable swaps; `maxDeposit` is then 0.
- **D7 Direct pair `burn`** (no router, no approval) is used for every burn (`rebalance`, `redeem`, `redeemInKind`): `pair.burn(vault, vault, ...)` with `msg.sender == from`. The router is used only to add liquidity and to swap. So exits do not depend on the router, its authorisation, or `approveForAll`.
- **D8 (ACCEPTED) No `emergencyExit`** (R3 had one): `redeemInKind` covers the exit; the spec said "if kept". No owner-forced unwinding of the band exists (owner can only `pause`).
- **D9 Not carried over from R3:** `deployIdle`, `maxWithdraw` sole-holder holdback, `initializeV2RiskParameters`, `onlyOwnerOrProxyAdmin`, the oracle contract, the tick libraries, the TWAP.

## 3. Interface-silent choices (what tests must pin)
- `PairValidationFailed(check)`: 1 zero address / empty field (incl. zero codehash) 2 asset == pairToken 3 factory.getLBPairInformation(asset, pairToken, binStep) != (pair, binStep) 4 pair.getFactory/getBinStep disagree 5 pair tokens not exactly {asset, pairToken} 6 router.getFactory != factory 7 pair hook (low 160 bits of getLBHooksParameters) != rewarder 8 rewarder.isLinked() false 9 voter (= rewarder.owner()) does not list the router as authorised manager 10 voter.dlmmRewarderFactory() (the beacon) does not list `rewarder` for `pair` 11 beacon.implementation().codehash != pinned 12 reward token zero or a leg 13 a feed has != 8 decimals, OR a feed is stale/bad at initialize (checked after the wiring is stored) 14 token decimals > 18. A failing external read inside the validator reverts with that call's own data (not `PairValidationFailed`).
- The beacon is derived at initialize (rewarder.owner().dlmmRewarderFactory()) and stored (`rewarderBeacon`); bit 32 is then live from `beacon.implementation().codehash` (the beacon is an immutable of the BeaconProxy, MEASURED in the verified source), plus hook == rewarder and `isLinked()`. Any failed read sets bit 32. Router de-authorisation is NOT a guard bit (the router/rewarder revert it on their own).
- `guardState()` is `(reasons != 0, latched, reasons)`: `unsafe` is LIVE only; callers must also read `latched`. `reasons` includes bits 16 and 32. Bit 16 is skipped unless BOTH feeds are healthy; |activeId - 2^23| > 4096 counts as deviating.
- Entry gate (deposit, mint, openBand, rebalance): `GuardLatched` first, then `GuardUnsafe(reasons)` (any live bit incl. 16, 32). `tripGuard()` latches only bits 1,2,4,8 and emits those; reverts `GuardUnsafe(0)` if none; callable repeatedly. `clearGuard()` (owner) reverts `GuardStillUnsafe(reasons)` while any live bit (1..32) is set, otherwise clears (also when not latched).
- `rebalance` check order: deadline (`DeadlineExpired`), `idSlippage > 2` (`ParamOutOfBounds`), no band (`NoBand`), in range (`NotOutOfRange`), entry gate, cooldown (`CooldownActive(readyAt)`, skipped while `lastRebalanceAt == 0`), daily cap (`DailyRebalanceCapReached`), `ActiveIdMoved`. Then swap limits: `SwapTooLarge(inValue, maxIn)` (inValue in asset units, maxIn = NAV x maxSwapBps), effective min out = max(`swapMinOut`, oracle out x (1 - maxRebalanceLossBps)) (clamped, not reverted), then `NavLossTooLarge(before, after)`. `swapIn == 0` skips the swap. Gated by `whenNotPaused`; only the rebalancer may call.
- `rebalanceAllowed()` reason bits: 1..32 guard bits as in `guardState`; 64 no band, 128 band exists and active in range, 256 cooldown, 512 daily cap, 1024 latched, 2048 paused. `readyAt` = lastRebalanceAt + cooldown (0 before the first), pushed to the next UTC day when the daily cap is hit. `ok == (reasonBits == 0)`. It does not check the keeper's caller rights or the swap/NAV checks.
- `rebalancesToday()` is 0 on a new UTC day (day = timestamp / 86400). `openBand` does not touch `lastRebalanceAt` or the daily counter and has no cooldown.
- Band is always the nominal 3 ids (active-1 .. active+1) after an add, even when a bin received nothing (zero-amount bins are dropped from the router call because the pair reverts `ZeroShares`; leftovers are refunded to the vault). Distribution (sums 1e18 each): Y 2/3 on -1, 1/3 on 0; X 1/3 on 0, 2/3 on +1 (even thirds by value at a 50/50 inventory). `openBand` evens the idle inventory itself (swaps (|asset - pairValue|)/2 of the over-held leg, same limits as `rebalance`).
- `activeIdDesired = expectedActiveId`, `idSlippage` <= 2 else `ParamOutOfBounds`; the vault checks `ActiveIdMoved` before burning and again just before adding (after its own swap), and the router checks too.
- Extra errors (additive): `ZeroAddress`, `ZeroAmount`, `ZeroShares`, `NotRebalancer`, `FeedInvalid(uint8 which)` (1 asset feed, 2 pair feed), `DeadlineExpired(uint256)`, `BandExists`, `NothingToDeploy`, `ExitFailed` (a pair view failed in an exit path or an exit paid nothing). Extra event `RebalancerUpdated(old, new)`. ERC-4626 errors are OZ's (`ERC4626ExceededMaxRedeem`, `ERC4626ExceededMaxWithdraw`).
- Public getters (not in the interface): `tokenX`, `tokenY`, `pairToken`, `assetIsX`, `pair`, `router`, `factory`, `rewarder`, `rewarderBeacon`, `rewardToken`, `rewarderImplCodehash`, `feedAsset`, `feedPair`, `binStep`, `rebalancer`, `lastRebalanceAt`. Guard-bit constants are internal (size); the values are in the interface comment and here.
- `redeemInKind(shares, receiver, owner_)` returns amounts in PAIR order (X then Y), i.e. `(USDt, USDC)` on the live pair; zero shares or receiver revert; allowance is spent when `msg.sender != owner_`. It reverts `ExitFailed` if it would pay nothing. Dust bins whose pro-rata burn amount or proceeds floor to zero are skipped (the pair reverts a whole burn on `ZeroAmount`/`ZeroAmountsOut`).
- Compiler: solc 0.8.35 via-IR, optimizer 200 (as vault-r3). `lib` is a tracked symlink `../lib` whose target `contracts/lib` is gitignored (three symlinks to the RobinhoodVaults libs); a fresh worktree needs `contracts/lib/{forge-std,openzeppelin-contracts,openzeppelin-contracts-upgradeable}` (OZ 5.3.0).

## 5. Unfavourable facts and open questions (read before relying on the contract)
0b. `redeem`/`withdraw` swap any non-zero USDt amount; on the real pair a 1 to 2 wei input may produce zero out and revert that exit (`redeemInKind` is unaffected). Not fixed (size margin); for W6.
1. **Not run on a fork.** Only `test/W2Smoke.t.sol` (15 tests, hand mocks, price 1:1, shares = value; covers init, cap, openBand, rebalance with swaps in both directions, a deposit while a band exists then a fold-in rebalance, mint, withdraw, redeem, in-kind, guard bits and latch, harvest, params; does NOT cover a one-sided inventory add (dropped-bin array shrink), `SwapTooLarge` by value, fuzz or a donation) was run; the real `DLMMPool` mint (composition fees on the active bin, `getSharesAndEffectiveAmountsIn` effective amounts), router and hook were not exercised. `amountXMin/YMin` and the NAV-loss check are the only protection against composition-fee surprises.
2. **Keeper power (cumulative daily loss cap stays keeper-side for the pilot, per the main thread; not in the contract).** Per rebalance the vault bounds the loss to `maxRebalanceLossBps` (default 0.5 %) of NAV and the swap to 60 % of NAV, at up to 48 a day, cooldown 120 s: a compromised keeper could in principle bleed up to the daily cap x 0.5 %. The spec has no cumulative daily loss limit; consider one. It cannot move funds out (no recipient parameter).
3. **Idle deposits earn nothing** until the next `openBand`/`rebalance` (decision 2). A deposit after the first band waits for an exit-triggered rebalance (MEASURED 5 to 6 a week at 3 bins).
4. **Cap vs donation**: donations count in NAV and only reduce headroom; gains can also lift NAV above the cap (D6, resolved).
5. **First-depositor inflation**: standard OZ virtual offset 0 (as R3); the 200 cap bounds it and the ceremony seeds the first deposit, but a griefing donation before the first deposit could cost a depositor a rounding loss.
6. **`clearGuard` grief**: bit 16 is live and can flicker, so a clear transaction can revert `GuardStillUnsafe` at the wrong block; retry.
7. **Forfeiture**: `harvestRewards` claims bins touched within 111 s of their last mint/burn and forfeits that bin's accrual since its last settlement (small). Unprivileged dust `redeemInKind` calls burn bins and can reset `lastModified` of the vault's bins; exits cannot be gated, so this is accepted. The keeper should harvest only well after a rebalance.
8. **Hook dependency** (spec section 3): a reverting rewarder/voter reverts `pair.burn`, hence every exit including `redeemInKind` (smoke test `test_failingHookBlocksInKind` shows exactly this with a mock). Nothing in the vault can change it.
9. `harvestRewards`'s `PharHarvested.totalAssets` is 0 when a feed is bad (a documented non-error value).
10. Tokens other than the two legs and PHAR sent to the vault are not recoverable (no sweep).
11. Size margin is 891 bytes: any addition needs another size pass.
