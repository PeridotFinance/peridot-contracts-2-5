Configuration `order-keeper/config/host.json` is generated by `order-keeper/deploy/make-config.py` from `ceremony/margin-addresses.env`; host script `order-keeper/deploy/orderkeeper-host.sh` (`bootstrap`, `stage`). Built and tested on a local fork (51 unit tests, 9 fork scenarios). Code: `order-keeper/` (TypeScript, ethers v5, its own package; it copies the operator's disciplines and imports nothing from `operator/` at run time). Not yet exercised by a real order.

## 1. What it does

An order is a stored take-profit or stop-loss on an open 2x long (`MarginOrderRegistry`). Anyone may execute a due order; the keeper does it for the owners. It holds **AVAX for gas only** and receives nothing: proceeds follow the existing close path to the position owner, the route is the one pinned pool, and `adapterData` is always empty (the adapter refuses anything else).

One cycle (default every 15 s):

1. **Read at the head, never archive.** `nextOrderId`, `registry.adapter()`, `adapter.registry()`, `adapter.executor()`, `paused()` in one Multicall3 call.
2. **Discover by id.** The registry has no list of orders, but ids run `1 .. nextOrderId-1` and `getOrder(id)` is public, so no event scan is needed. The keeper reads every id from `highWater` (new ones, at most `maxIdsPerCycle` per cycle) plus every id it last saw OPEN. A terminal status (EXECUTED, CANCELLED, EXPIRED) never reverts to OPEN, so those ids are dropped for good. Reading cost is the number of OPEN orders (at most 4 per position, at most 30 days old, expired ones swept), not the history. An id that reads as NONE below `nextOrderId` (a node that lags) is not skipped over; `nextOrderId` falling below what was already read halts.
3. **Decide with `canExecute(id)`** (pure function `src/decide.ts`):

| canExecute reason | Action |
| --- | --- |
| 0 executable | execute (stop-losses before take-profits, then by id) |
| 2 expired, 3 position inactive, 4 owner changed | **sweep**: `executeOrder` marks it EXPIRED / CANCELLED (it does not revert) so the slot is freed; `limits.sweep` can switch it off |
| 5 oracle unavailable | wait, send nothing, **alert** `oracle:unavailable` (the order stays open, nothing is cancelled) |
| 6 trigger not reached, 7 paused | wait (a paused registry also raises `registry:paused`; nothing is sent, not even a sweep, because `executeOrder` reverts while paused) |
| 1 not open | final |

4. **Simulate** exactly what would be sent (`eth_call` of `executeOrder(id, 0x)` from the keeper address; the returned bool must match the intent, true for an execution, false for a sweep) and estimate gas (x 1.3, ceiling `maxGasLimit`).
5. **Persist the pending marker**, send (fee cap, gas floor, per-cycle and per-day limits), **read back**, clear the marker.

## 2. Discipline (same as `operator/src/executor.ts`)

- **Pending marker before every transaction** (executions and sweeps); one found at start **halts** the process with no read and no send. A human checks the wallet's transactions and the order, then clears `pending` and `halted` in the state file.
- **Read-back after every mined transaction**, from the receipt and from state at the receipt's block (and the block before, with the operator's retry-then-latest fallback for a non-archive node). Execution branch: order status EXECUTED; exactly one `OrderExecuted` naming this order, this keeper as executor and the order's `closeBps`, at a price that crosses the trigger; exactly one `PositionClosed` from the margin executor with the same `closeBps` and `returnedMarginPTokens` equal to `OrderExecuted.returnedMargin`; position CLOSED if `fullyClosed` else ACTIVE; the owner's vault `freeBalance(owner, marginPToken)` rose by exactly that amount; the keeper wallet's balances of the three pTokens, USDC and WAVAX did not change; the order is out of `openOrdersOf`, and if the position ended no order is left open on it (mutual cancellation). Sweep branch: status CANCELLED (reason 2 or 3) or EXPIRED with the matching event, **no** `OrderExecuted` or `PositionClosed`, position status unchanged, no balance change. **Any mismatch halts.** (Difference from the operator: after a read-back mismatch the operator leaves its `pending` marker set and sets `halted`; this keeper clears `pending` (the transaction is known and was read back) and sets only `halted`, whose reason carries the transaction hash. A `pending` found at start still halts.)
- **Halt triggers:** pending marker at start; signer address is not `keeper.address`; wiring drift (registry/adapter/executor addresses differ from the configuration); read-back mismatch; `nextOrderId` going backwards; any error after the marker was set (the transaction may or may not be mined); `maxMinedRevertsPerDay` mined reverts after passing simulations (each cost gas). A read error before any send is an ordinary failed cycle (warning `cycle:failed`, nothing was sent).
- **Simulate-revert cooldown:** known waits (`TriggerNotReached`, `OracleUnavailable`, `ExecutionPaused`, adapter `InvalidClose` 5/6, swap module `SwapError` 5 and 7, `InsufficientOutput`) cool the order down 30 s, doubling per consecutive failure to 300 s; unclassified reverts 900 s and a warning; a mined revert 900 s. An order that has been due but unfillable for `unfilledAlertSeconds` (600) raises a warning (a stop-loss that cannot fill: pool depth, liquidation is the backstop; **the keeper never loosens a limit**). A cooldown is dropped when the order stops being due.
- **Signer:** Foundry keystore (mode 600 required), password from the environment variable named in the config; the signer's address must equal `keeper.address` or the process refuses to start; chain id 43114 checked at start.
- **No secrets in config, state or logs:** the config file is scanned for key-shaped text and URLs with keys; every printed or alerted string passes `mask()`; the endpoints and the password exist only in the environment.
- **Alerts:** the operator's `AlertManager` (de-duplicated, masked; channels `log`, `telegram`, `webhook`). Keys: `keeper:halted` (crit), `oracle:unavailable`, `registry:paused`, `keeper:gas` (crit), `order:<id>:unfilled`, `order:<id>:simfail`, `node:stale`, `registry:anomaly`, `logs:*`, `cycle:failed`; an info notice for every executed / swept order.

## 3. Logs and the free tier

State reads are at the head through the state endpoint (`AVALANCHE_MAINNET_RPC_URL`, free tier is enough). `eth_getLogs` goes only to a **separate** endpoint (`AVALANCHE_LOGS_RPC_URL`) and only for an **optional cross-check** (`logs.enabled`): `OrderCreated` events from the head forward, in chunks of `chunkBlocks` (10 for the free tier, up to 100 for the Avalanche public RPC), at most `maxChunksPerCycle` per cycle, paced (`minIntervalMs`) with the operator's 429 back-off (60 s doubling to 900 s, in `src/logpace.ts`). It raises a critical alert if the logs show an order id the id scan has not read (a state endpoint serving old state); it is suppressed while the id scan is still catching up (a cycle that hit `maxIdsPerCycle`). A rate-limited or failing log endpoint is a warning, never a stop and never a halt. There is deliberately no history scan.

## 4. Configuration and state

`order-keeper/config/order-keeper.example.json` (template, refused while any `UNSET` remains). Addresses: `registry`, `closeAdapter`, `marginExecutor`, `marginVault`, `keeper.address`. Limits (proposals, not results): fee cap 100 gwei, gas floor 0.04 AVAX (the fleet's floor; the pilot wallets are funded with 0.1 AVAX), 3 sends per cycle, 60 per day, 3 mined reverts per day halt, gas ceiling 4,000,000 (the rehearsal measured 1.47 M and this fork run 1.66 to 1.68 M gas for a full close; the estimate is multiplied by 1.3), poll 15 s, block lag limit 60 s. State: `monitor.statePath` on the mounted volume, written atomically with fsync, mode 600; refused (exit 78) if it is corrupt or belongs to another registry (never reset silently).

## 5. How it would be hosted

A **separate Droplet role** next to the four pilot roles (`avalanche-pilot-hosts.md`): its own Droplet, its own 1 GiB volume at `/mnt/pilot_orderkeeper_data` (config, keystore, state), its own throwaway keystore and its own `/etc/pilot/orderkeeper.env` (root, 600) holding `AVALANCHE_MAINNET_RPC_URL`, `AVALANCHE_LOGS_RPC_URL` and `ORDER_KEEPER_KEYSTORE_PASSWORD`. Image: `order-keeper/Dockerfile` (same shape as `operator/Dockerfile`); unit template: `order-keeper/deploy/pilot-orderkeeper.service.example` (read-only container, `--cap-drop ALL`, `Restart=always`, `docker stop -t 60` so a cycle in flight can finish). Not provisioned, not staged. The wallet needs gas only: size it for the per-day send limit at the fee cap (60 x about 1.5 M gas is the worst case; a typical day is a handful of sweeps and executions). Run **one instance per registry**: two instances would race, and the pending marker only protects one state file. An executor is permissionless, so a second independent keeper elsewhere is safe for the owners (the loser's simulation reverts `OrderNotOpen`, which is classified final and costs nothing) but they must not share a wallet.

**Why the position stayed ACTIVE after the first funded liquidation (the cause).** A funded liquidation takes only part of the debt unless the health factor is at or below the pair's `fullLiquidationHealthBps`. The pair's risk values on this stack: `maxLiquidationBps` 5000, `fullLiquidationHealthBps` 5000, `liquidationTargetBps` 12500, `maxSlippageBps` 100. At -36 % the health factor was 9,020 bp: the call repaid 19.60 USDC (about half) and the position stayed ACTIVE; at -48 % it was 7,872 bp: another half (9.80 USDC), ACTIVE; at -60 % it was 3,891 bp, below 5,000: the whole remainder was taken and the position became LIQUIDATED. So a partial liquidation leaves the position and its orders live (they can still execute against the remainder); only a deep fall (or dust debt) ends it, and the orders then die on the keeper's sweep. (With `minSeizeValueBps` 10,000 the funded route declined small positions with `LiquidationError(32)` in my debug runs; the test passes 0.)

## 7. Things in the contracts that matter to a keeper

- **Liquidation does not cancel orders.** Nothing in a liquidation touches the registry; the orders die on the **next execution attempt** (reason 2 or 3 in the registry's terms: position inactive). The keeper's sweep is therefore what frees them. A partial liquidation leaves the position ACTIVE: its orders stay live and can still execute against the remainder.
- `canExecute` computes "paused" last, but `executeOrder` reverts `ExecutionPaused` first: a paused registry blocks sweeping too.
- The registry has no list of orders and no `orders(i)` getter: the function is `getOrder(id)`, ids run from 1 to `nextOrderId - 1`.
- `canExecute` reason 7 (paused) is the reference implementation's own code, not in the spec's table.
- The adapter's minimum is derived from the oracle, not from the pool; the swap module independently refuses a minimum looser than the oracle floor (`SwapError(5)`), and a pool that pays less than the floor reverts in the router (`Too little received`) or the module (`SwapError(7)`).
- A vault `freeBalance` credit can exceed `returnedMargin` (rewards settled in the same call).
