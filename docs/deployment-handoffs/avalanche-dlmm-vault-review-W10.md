# PharaohDlmmVault: independent adversarial review (W10), 15 Nov 2026

Reviewer: W10, read-only. Code reviewed: integration worktree `.wt-dlmm-int`, branch `feat/dlmm-vault-int`, HEAD `a6e1cb70` (includes fix `182d272c`, a future `updatedAt` is a bad feed). Files: `contracts/vault-dlmm/src/PharaohDlmmVault.sol` (840 lines), `PharaohDlmmPairValidator.sol`, `IPharaohDlmmVault.sol`, `interfaces/`, `DEVIATIONS.md`, spec, evaluation sections 7 and 8, risk register, and the R3 base for comparison. I did not rely on the tests. Nothing was signed, sent or pushed; no chain access was used. Labels: MEASURED (I ran or read it), DERIVED (arithmetic on stated figures), ESTIMATED (assumption). Line numbers are in `PharaohDlmmVault.sol` unless named.

## Verdict
No Critical or High finding in the contract logic. Nothing is a hard ceremony blocker. Two Medium findings concern the keeper bound (F1, F2) and have small fixes; I recommend applying F1 before the ceremony (it changes the codehash, so tests, W7 and the fork run must be repeated). The operator must knowingly accept F2 and the hook dependency (risk register row 1) otherwise.

## Findings, ranked

### F1. Medium. The 0.5 % per-rebalance bound is only an immediate, oracle-marked bound; the band is minted at an unchecked post-swap price (lines 427-438, 380-396, 550-554)
`rebalance` and `openBand` check pool-versus-oracle deviation (bit 16, 60 bp) once, at entry (`_requireEntryOk`, line 416 / 376). The vault then swaps (up to 60 % of NAV), and `_addBand` mints around the real active id read after the swap. The only checks after the swap are `_checkActive` against the CALLER's `expectedActiveId` (useless against a thief, who passes the id he engineered) and `_checkNavLoss` (line 545), which marks NAV at the ORACLE immediately after the mint. A band minted at an active price off the oracle shows no NAV loss at that instant; the loss arrives when an arbitrageur trades against the mispriced bins afterwards.
Exploit (DERIVED, not run): a stolen keeper key plus a pool whale (or anyone willing to push the pool 55 bp, inside the 60 bp gate) calls `rebalance` with `swapMinOut = 0`, `amountXMin/YMin = 0`, `expectedActiveId` = the pushed id. Swap loss up to the floor, 0.5 % of ~USD 100 = USD 0.50; then the band is minted 0.55 % off the oracle and the back-run takes about 0.55 % of the ~USD 100 sitting on the mispriced side, about USD 0.55. Total about 0.5 % NAV, of which only the swap half is visible to `NavLossTooLarge`; in a thinned pool (a whale withdrew near-peg depth, so the vault's own swap moves the active id several bins while the average still passes the 0.5 % floor) the post-mint part is larger and is bounded by nothing in the vault. ESTIMATED total per rebalance: 0.5 % to about 1.1 % of NAV.
Honest keeper: protected, because it sets `expectedActiveId` to the predicted post-swap id with `idSlippage` <= 2 (2 bp).
Fix (about 60 to 150 bytes; MEASURED runtime margin is 989 B): after `_guardedSwap` and before `_addBand`, in both `rebalance` and `openBand`: `(uint256 r,,) = _evaluate(); if (r & POOL_ORACLE_DEVIATION != 0) revert GuardUnsafe(r);` (or call `_poolDeviates(pa, pp)` directly with the prices already in hand).
Blocks ceremony: no (loss bounded by the 200 cap); recommended before.

### F2. Medium. The daily cap resets at UTC midnight; the worst case is 96 rebalances in about 3.2 h, not 48 a day (lines 417-424, 761-766)
Cooldown 120 s plus `_day = timestamp / 1 days` lets a keeper-key thief do 48 before and 48 after midnight: 95 x 120 s = 11,400 s = 3.17 h. DERIVED at the 200 cap, at the stated 0.5 % per rebalance, compounding:
- 48 in a day: 1 - 0.995^48 = 21.4 % of NAV = USD 42.8 (simple sum 24 % = USD 48, as in risk register row 6).
- 96 across midnight in 3.2 h: 1 - 0.995^96 = 38.2 % = USD 76.4.
- If F1's post-mint leak is real (ESTIMATED 1.1 % per rebalance): 41 % (USD 82) for 48, 65 % (USD 130) for 96.
Each rebalance also needs the active bin outside the band, which the thief (or a whale) must force each time: a swap across 2 bins, cheap for a whale holding the depth (97 % of the pool is two addresses). Sandwiching the vault's own swap cannot beat the vault floor (oracle minus `maxRebalanceLossBps`) and, with a thief's `swapMinOut = 0`, extracts up to that floor; with an honest keeper it extracts only the slack between the keeper's `swapMinOut` and the fill. Value cannot leave except as trading loss: there is no recipient argument.
Fix: a rolling loss budget instead of a day counter (a `uint32` bps budget refilled linearly, e.g. 50 bp per 30 min, capped at 100 bp; charge `navBefore - navAfter` per rebalance; about 150 B). Cheaper alternative: operational (alert plus Safe `pause()` within minutes; `pause` blocks `rebalance`, never exits).
Blocks ceremony: no, but the operator must accept the number above (it is larger than the "48 a day" wording suggests).

### F3. Low. `tripGuard` latch needs a Safe transaction to clear; a real Chainlink blip latches it for everyone (lines 589-602)
Answers to the specific questions: (a) Can anyone latch with a flash-moved feed? No: the feeds are Chainlink aggregator proxies, not movable in a transaction; the pool price is only bit 16, which is non-latchable (`LATCHABLE_MASK = 15`), so pool manipulation cannot latch (the fork test `test_poolMoveAloneCannotLatch` agrees). (b) Can the latch be bypassed? No: `GuardLatched` is checked in `deposit`, `mint` (via `_requireEntryOk`), `openBand`, `rebalance`, and `maxDeposit/maxMint` return 0; there is no other entry path (`_deposit` is internal, no permit-deposit). (c) Cost: the calibration says a 50 bp leg band would have latched on two real USDT feed episodes since 2023 (+56 bp for 79 s, +66 bp for 17 min). Anyone, including a griefer, can then latch during such a window; only `clearGuard` (Safe, Ledger 1-of-1) releases it, so the band stays out of range and the keeper halts until a human acts. Exits are unaffected. `clearGuard` can also revert at a flickering bit 16 (known, DEVIATIONS 5.6).
Fix: none required for safety; consider `legBandBps` 75 (the W-CAL option). Blocks ceremony: no.

### F4. Low. PHAR dust-burn forfeiture (risk register row 9, left to this review)
Mechanism (verified in code, lines 264-281, 305-351): `redeemInKind` by anyone with shares calls the pair's `burn` on the vault's bins, which resets the vault's `lastModified` at the rewarder; a second touch within 111 s forfeits the PHAR accrued since the previous settlement. The attacker needs at least about 3 share-wei (below that every bin's proceeds floor to zero, the bin is skipped and the call reverts `ExitFailed`; W6 measured 3 shares), so capital is about USD 0.000003 and the shares are returned in kind.
Cost to attacker (ESTIMATED: gas 0.3 to 0.4 M per call incl. the hook, 3.5 gwei median, AVAX USD 8.58): about USD 0.01 per call; one call per 111 s = 778 calls a day = about USD 8 a day.
Loss to the vault (DERIVED from the W6 measurement: 300 s of accrual = 5.318e15 wei PHAR for a USD 100 vault): 1.53 PHAR a day = about USD 0.063 a day at USD 0.041; about USD 0.13 a day at the 200 cap. The attacker pays roughly 60x to 130x what he destroys; he would need a PHAR emission about 60x today's to break even. Also the loss is the Safe's PHAR stream, not depositor principal. Severity Low, uneconomic except as spite or as a competitor's tool. No code fix is available that keeps exits ungated (pro-rata burn must touch the bins); accept and monitor `PharHarvested` rate. Blocks ceremony: no.

### F5. Low. Ceremony ordering: the first deposit cannot be seeded while paused; donation can then grief it (lines 214, 181, 195)
The contract does start PAUSED (`_pause()` at line 181; risk register row 8 and ceremony question B read as if it did not, so they look stale). `deposit` is `whenNotPaused`, so seeding needs an `unpause()` first. If `unpause` and the Ledger deposit are separate transactions, a front-runner can deposit 1 wei (1 share) and donate USD 199.99 (direct transfer counts in NAV): the Ledger's deposit then reverts `CapExceeded`, or any deposit below about half the donation reverts `ZeroShares` (price per share is (N+1)/(S+1) with OZ offset 0). The attacker is the sole holder, so `redeemInKind` returns the donation: the attack costs gas only and can repeat each block.
Inflation analysis (DERIVED, important): with OZ 5.3 offset 0 (virtual 1 share and 1 asset) and redemption on the REAL supply (`shares/supply` pro-rata, lines 305-309), a donation attacker never profits and a victim never loses more than rounding: for S = 1, N = 1 + D, a victim deposit d gets floor(2d/(D+2)) shares and redeems (1 + D + d) x shares/(shares+1), which is >= d for every d that does not revert. The only damage is denial (`ZeroShares`/`CapExceeded`). Deposit floors, mint and withdraw ceil, in-kind floors, and skipped dust bins stay with holders (rounding always favours the vault; I found no farmable rounding).
Fix: procedure only: one Safe MultiSend [`unpause`, `approve`, `deposit`] (or `unpause` and deposit in the same Safe batch). Blocks ceremony: no, but put it in the command list.

### F6. Low. `redeem`/`withdraw` have no min-out and trust the router's return value (lines 236-259, 283-300, 467-483)
(a) The USDt part of an exit is swapped with min out = oracle x (1 - 0.5 %) and the redeemer cannot tighten it: a sandwicher extracts up to 0.5 % of that part (about 0.25 % of the redemption at 50/50; USD 0.50 at 200), borne by the redeemer only. Interface is frozen; frontend should prefer `redeemInKind` or document it. (b) `_swap` returns the router's `amountOut` and `_payOutAsset` pays `assetAmt + amountOut` (line 295-298) without a balance delta; a router that over-reports would pay the redeemer out of other holders' idle USDC. The router is validated by factory and voter authorisation at init but not code-pinned. Fix (about 40 B): measure `balanceOf(asset)` before and after the swap. Blocks ceremony: no.

### F7. Low. Ownership: single-step transfer and `renounceOwnership` exposed
`OwnableUpgradeable` is inherited unchanged. A mistaken transfer or renounce (a Safe transaction) permanently loses `pause`, `unpause`, `clearGuard`, params, cap and rebalancer rotation (the vault would stay latched or paused forever; exits still work). Fix: override `renounceOwnership` to revert (about 30 B) and use a two-step flow in the ceremony. Blocks ceremony: no.

### F8. Info (batch)
- Validator (lines 31-75) pins decimals only for the feeds; a swapped or wrong feed address (e.g. USDT/USD as `feedAsset`) passes if it has 8 decimals and is fresh. The ceremony read-back must read `description()` and the answers. Initialize also accepts a feed already outside the leg band at deployment (13b checks only stale/bad). A cheap strengthening: revert at init when bits 4 or 8 hold.
- `rebalanceCooldown` hard minimum 111 (line 763) equals the forfeiture window, but the rewarder forfeits at `<= 111` s; the lower bound should be 112.
- Read-only reentrancy: `redeem*` burn shares (line 275/289) before the bins are drained, so `totalAssets`/`convertToAssets` read mid-exit is inflated; the only external calls in that window are the pair (hook is Pharaoh code) and the two ERC-20s, so no attacker callback exists today. A consumer that prices shares (Peridot oracle) must treat `convertToAssets` as spot (composition shifts by up to about 0.07 % of NAV with a swap inside the band, MEASURED by evaluation) and handle the `FeedInvalid` revert.
- `withdraw(assets)` can pay less than `assets` and `previewRedeem` overstates (DEVIATIONS D1); ERC-4626 integrators beware.
- After a full exit (`shares == supply`, line 306, 350) bins whose proceeds floor to zero are skipped and `_hasBand` is cleared: dust LB shares (< 1 raw unit per token per bin) stay orphaned and uncounted, re-counted only if a later band reuses the id. No value risk.
- Upgrade: the ProxyAdmin owner (Safe, 1-of-1) can replace the implementation, including the 200 ceiling, at any time with no delay (already risk register row 5).
- Reward token is fixed at init (line 152), validated non-zero and not a leg (check 12), so a changed rewarder token can never make `harvestRewards` forward USDC or USDt; a hostile token can only make `harvestRewards` revert, which does not touch exits.

## Areas where I found nothing
- Pause: `redeem`, `withdraw`, `redeemInKind`, `harvestRewards`, `tripGuard` carry no `whenNotPaused` (lines 236, 246, 264); only deposit, mint, openBand, rebalance do. Pause cannot block exits.
- `redeemInKind` and `_sliceOut`: no oracle read, no swap, no router call, no guard/latch/cooldown/keeper/codehash reference (lines 264-281, 305-359). Under any depeg or dead feed it works; `redeem`/`withdraw` revert `FeedInvalid` or at the swap floor, as documented.
- Reentrancy: every state-changing entry point except `tripGuard`, `clearGuard` and admin setters is `nonReentrant`; LB shares have no ERC-1155 receiver callback (non-transferable), tokens are plain ERC-20s.
- Approvals: `approveForAll` is never used (direct `pair.burn`); every router approval is set to 0 after use (lines 478-482, 516-538), `forceApprove` handles USDT.
- Cap: `deposit`/`mint` check `totalAssets()+assets <= cap` (line 727); donation only reduces headroom; gains can exceed the cap (D6); no direct-transfer, mint or rebasing path bypasses it.
- Gas DoS: the band is fixed at 3 bins (`_upper - _lower + 1`); no per-user loops. Overflow: plain `a*b/c` bounded far below 2^256 (D5), reasoned against a worst case of 1e16 raw units x 2^128 shares per unit.
- Proxy/init: implementation constructor calls `_disableInitializers`; the validator is stateless, has no selfdestruct or delegatecall; the vault has no `delegatecall` or `selfdestruct`; storage is non-namespaced state after namespaced OZ bases with a 40-slot gap; `initialize` sets owner and rebalancer from params, caps at the ceiling, ends paused. Initializer front-run is impossible if the proxy is created with init data in its constructor (ceremony design).
- EIP-170: MEASURED today with `forge build --sizes` (output to a scratch directory): runtime 23,587 B, margin 989 B; initcode 27,632 B; validator 3,680 B. F1 and F6 fixes fit; F2 plus F7 likely fit but need a size pass.
