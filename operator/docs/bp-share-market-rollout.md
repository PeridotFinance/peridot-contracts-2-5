# bpPHAR-USDC (DLMM vault-share market): operator, executor and treasury keeper rollout

Prepared 18 Nov 2026 (wrapper-v2 fallback keeper added 21 Nov) offline (no RPC, no docker, nothing signed or deployed). Branch `feat/bp-dlmm-keepers`, built on `fix/alert-sink-nonfatal-operator` (so the non-fatal alert sink is in the same build). All hosts stay on alerts channel `log` (journal JSON lines) until the Telegram bot exists.

## What the new build does
1. **Oracle allow-list.** `controller.oracle()` must be exactly one of {`deployment.oracle` = the old GuardedAvalanchePriceOracle, `deployment.oracleWrapper` = the wrapper (a config value, nothing hard-coded)}. Any other address still fails closed (the cycle throws, the monitor goes blind and pages). The same build runs before and after the swap. Without `oracleWrapper` in the config the behaviour is the old one (only the guarded oracle), so the wrapper address must be in the config BEFORE the swap. All price reads (`getUnderlyingPrice(pToken)` for every listed market) go to whatever `controller.oracle()` returned at the snapshot block; the keepers use no other oracle function (no `getPrice(asset)`, `marketAsset`, `source()`, `feeds(...)`).
2. **Share collateral in the liquidator (executor, op1 and op2): SEIZE-AND-KEEP.** For an account in shortfall that holds the share pToken it repays USDC from its own inventory and calls `liquidateBorrow(borrower, repay, pShare)`; it KEEPS the seized pTokens (no redeem, no swap; the pWAVAX path with redeem and conversion is unchanged and still chosen for accounts without share collateral). Bounds per call: close factor, 92.4% of the collateral's oracle value, inventory, per-call cap, rolling 24 h cap, and a ceiling on the oracle value of share pTokens the operator already holds (it never sells them). Before anything is sent: `liquidateCalculateSeizeTokens` is checked against the borrower's balance (the repayment is cut to fit), and the value received (net of the pToken's `protocolSeizeShareMantissa`) must be at least the USDC repaid. Then: approve exactly the repayment, simulate, send, read back (USDC delta, event fields, pToken delta == event seize minus protocol share), reset the allowance, HALT on any mismatch. Seized pTokens are recorded in the round (`collateralPToken`, `keptCollateral`) and are never counted as USDC inventory. The alert text says what was seized and that it was kept.
3. **Treasury keeper: ALERT-ONLY for share collateral.** It cannot price shares independently, so it never repays an account that holds the share pToken (excluded from the payable set, re-checked at execution, and the monitor raises `acct:<account>:share-collateral`, audience treasury-signers, text starting "... ALERT-ONLY: the treasury keeper cannot price vault shares independently ..."). Even without the config block the rule already returns NO_REFERENCE_PRICE for such accounts (no reference price exists for that market), so nothing could be paid; the block makes it explicit and loud. The monitor does not raise the 15-minute "unknown price" page for that expected condition. Other accounts: unchanged.

4. **Wrapper fallback keeper (wrapper v2, added 21 Nov): `poke()` loop on ONE host, monitoring on EVERY host.** The v2 wrapper (`PharaohDlmmShareOracle`) prices the share from the vault's live answer; when the vault cannot answer (one of its two Chainlink feeds is stale) it serves the stored value x 97% for at most 24 h after the last successful `poke()`. Without a recurring poke the fallback expires 24 h after deploy (the constructor counts as the first store), after which the share price is 0 during any feed outage. The poke is permissionless and moves no funds (gas only).
   * **Poke loop** (`src/poke.ts`, config `shareCollateral.poke`, DEFAULT OFF: an absent block or `enabled: false` makes the host do nothing). Only the host with `enabled: true` runs it: **op1 gets `enabled: true`; op2 and the treasury-keeper host get `enabled: false`** (they still monitor). It runs in the executor process of that host, as its own step after every cycle (after the liquidation step; a failing monitor cycle or a halted executor does not stop it), with the executor wallet (the operator wallet), so `executor.enabled` must be true there. Each round: read `shareState()`; act only when the vault can answer (`liveAssetsPerShare > 0`) AND `now - storedAt >= pokeMinAgeSeconds` (default 3,700 s: a bit over the wrapper's 1 h upward gate, so a poke that moves the value up is never refused). Then, in this order: no earlier poke in flight (a persisted record for 10 minutes, and the wallet's pending nonce equals its latest nonce), RPC block fresh, fee under `maxFeeGwei`, wallet AVAX above `minGasWei`, `poke()` simulated with eth_call from the operator wallet (a `false` or a revert sends NOTHING: no gas is spent on a refused poke), gas estimate x 1.5 (an estimate above 500,000 is refused as "not a poke"), send, wait for the receipt, read `shareState()` back and check the stored time moved. After a failure there is no new attempt for 300 s. State lives in the host's state file (`poke`), so a restart neither double-sends nor forgets. Every failure becomes a `share:poke-error` warning; nothing in this loop throws, and the alert sink stays non-fatal as in the base branch.
   * **Monitoring** (every host that has `deployment.oracleWrapper` and the `shareCollateral` block, whether or not it pokes; read only, at the cycle's snapshot block; alert channel stays `log`): see "Alerts" below.
   * **The liquidation route is untouched.** The executor reads the controller's own price and `getAccountLiquidity`; it has no knowledge of the fallback (a test pins that the same transactions are sent with the live price and with the fallback price, and that `executor.ts`/`share.ts` contain no fallback symbols). While the price is the fallback price (97% of the last good value) the route works as before at that price; at price 0 it does nothing (route off, existing `executor:share-price:<op>` warning).

## Config (public values only), additions to `config/hosts/<role>.json`
Do NOT regenerate the host files with `deploy/make-host-configs.py` after adding these (it rebuilds them from the template and drops the additions).

```json
"deployment": {
  "controller": "0xbE938cD7C25E0E4d0604Fa3F9f0a8b5b67b3D51A",
  "pWavax": "0x12f1F4Fc057a76f473B781ce2Fa88E55ef8581B1",
  "pUsdc": "0x0f7849CD9E54ffb027aacaEec82007cca9470098",
  "oracle": "0x7BAB5406Cb4929f9b9492e1b2a43b65BF93AaFC0",
  "oracleWrapper": "<WRAPPER ADDRESS after its deployment>",
  "deploymentBlock": 99846691
},
"shareCollateral": {
  "pToken": "<bpPHAR-USDC pToken>",
  "underlying": "0x278B1b625C74B1926C5F989ddE601f3C5Ba27f7D",
  "liquidation": { "enabled": false, "maxRepayPerCallUsdc": 60, "dailyRepayCapUsdc": 100, "minRepayUsdc": 1, "retryCooldownSeconds": 30, "maxHeldValueUsdc": 200 },
  "poke": { "enabled": true, "pokeMinAgeSeconds": 3700, "maxFeeGwei": 100, "minGasWei": "10000000000000000" }
}
```
The `poke` block (all three roles, a ready-to-edit copy is `config/share-collateral.example.json`; it is not a host file and its placeholders make it invalid until filled):
* **op1: `"poke": { "enabled": true, ... }`. op2 and the treasury-keeper host: `"poke": { "enabled": false }`** (or omit the block). Exactly one host pokes.
* `pokeMinAgeSeconds` (optional, default 3700, allowed 3601..10000): poke only when the stored value is at least this old. It must stay above the wrapper's 1 h upward gate and below the 3 h "poke stalled" alert.
* `maxFeeGwei` (optional, default `executor.maxFeeGwei`): no poke while the network max fee is above it (the "stalled" alert then fires after 3 h).
* `minGasWei` (optional, default `executor.minGasWei`): no poke below this AVAX balance (the example uses 0.01 AVAX, lower than op1's 0.04 AVAX executor floor, so a drained liquidator still pokes).
* Validation: `enabled: true` needs `executor.enabled` and `deployment.oracleWrapper`; `validate-config` checks it offline. The start-up line `{"startup":{...,"shareCollateral":{...,"pokeEnabled":true}}}` shows it per host.
* `config/hosts/*.json` in the repo carry NO share/wrapper blocks yet (the wrapper and pToken addresses do not exist until the ceremony; a placeholder would make the file refused). Add the blocks by hand after the ceremony, as above; a test checks that the example merges into all three host files and validates.
* op1 / op2: both blocks; set `liquidation.enabled` to `true` only at step 6 below. `maxHeldValueUsdc` (200) is the new ceiling on the share pTokens an operator may hold (flow caps alone do not bound a stock that is never sold): a proposal, not a measured value; the user decides it.
* treasury keeper host: the same two blocks with `"liquidation": { "enabled": false }` (nothing else is needed there).
* `underlying` is the vault share token (the ERC-4626 vault proxy); the executor turns the share route OFF and alerts crit if the market's `underlying()` differs.
* The caps are per operator and separate from the margin caps: worst case per operator per 24 h is 100 USDC (margin) plus 100 USDC (share) of repayments. Say if one combined cap is wanted.
* A config with the share block but a market not yet listed is valid: the route is simply inactive.

## Order of operations
0. Before touching a host, on that host: `docker tag pilot-operator:local pilot-operator:pre-bp-share` (keeps the running image reachable for a rollback; see Provenance).
1. Deploy the wrapper (no controller change yet) and note its address. Listing ceremony items (pToken, seed, flags) may follow in whatever order the ceremony says, but the controller's `oracle()` must still be the old oracle until step 4.
2. Put `oracleWrapper` (and the `shareCollateral` block, liquidation disabled) in `config/hosts/{op1,op2,keeper}.json`. **In the same edit set `shareCollateral.poke.enabled: true` on op1 and `false` on op2 and the treasury host** (stage 1: the poke config goes out together with the allow-list). Do stage 1 within 24 h of the wrapper deployment: the fallback window is counted from the deployment, and the first poke is due 3,700 s after it. Fund the op1 wallet first (see "Gas for the poke").
3. Stage the NEW image and config on op1, op2 and the treasury keeper host, ONE host at a time, when its journal shows no in-flight transaction (a restart between transactions leaves a pending marker that halts the process): `deploy/stage-host.sh <op1|op2|keeper> <ip>` (builds `pilot-operator:local` on the Droplet from this tree and pushes the config; it starts nothing), then `ssh root@<ip> systemctl restart pilot`. Verify with `contracts/tools/grant-host-status.sh` (unit active, container up, fresh last log line, wallet balance) and read the journal: normal cycles, no `monitor cycle failed`, no `configuration refused`. Also check, per host, that the wrapper address is really in the config the container reads: `ssh root@<ip> "grep -c oracleWrapper /mnt/pilot_<role>_data/config/host.json"` must print 1 (the status script does NOT see this: a host on the new image WITHOUT the wrapper in its config looks healthy until the swap and then goes blind), and the journal's start-up line `{"startup":{"oracleAllowList":[...],"shareCollateral":...}}` (printed by every `run`/`check`/`validate-config`) must list BOTH the guarded oracle and the wrapper. `validate-config` can be run offline on the file before staging. All three hosts must be on the new build and config before step 4. On op1 the journal must then show, within about an hour of the last store, `{"poke":{"result":"poked",...}}` (rounds with nothing to do print nothing), and `cast call <wrapper> "shareState()"` (or the monitor report) shows `storedAt` moving about hourly.
4. The oracle swap ceremony (controller `_setPriceOracle(wrapper)` by the Ledger admin). Right after it, re-run the status script and confirm the next cycles on all three hosts are normal (no "neither the configured guarded oracle nor the configured oracle wrapper" in the journal). If any host shows that text, roll the oracle back (below) first, then fix the config.
5. CF raise on the share market only after step 4 is verified on all three hosts.
6. Before (or with) the CF raise: set `liquidation.enabled` to `true` on op1 and op2, stage the config only (`SKIP_BUILD=1 deploy/stage-host.sh <role> <ip>`), restart, check the journal.

## Alerts (wrapper fallback), every host, channel `log` (journal JSON lines; `severity` is `crit` or `warn`)
Keys are stable and de-duplicated by the alert manager (one message when raised, one `resolved` when cleared; `share:fallback*` and `share:price-zero` also escalate at 1 h / 4 h / 24 h).

| key | severity | raised when | what to do |
|---|---|---|---|
| `share:fallback` ("share price served from fallback") | crit | `shareState().usingFallback`: the vault cannot value its shares, the controller uses the stored value x 97% | look at the vault's feeds (USDC/USD, USDT/USD); the message gives live/stored values and the window left. Nothing is broken yet, but the clock is running |
| `share:fallback-expiring` ("fallback time left below 6 h") | crit | using the fallback and `fallbackSecondsLeft < 21,600` | the price goes to 0 when it runs out: every account that entered the share market is then frozen (no borrow, no redeem, no exit, no liquidation). Escalate to the admin: fix the feed or prepare the oracle rollback |
| `share:price-zero` ("wrapper price for the share market is 0") | crit | the wrapper's own `getUnderlyingPrice(shareMarket)` is 0 (read directly from the wrapper, whichever oracle the controller uses) | the account-freeze condition. Causes: 24 h fallback expired, vault BROKEN (`asset()` changed/unreadable, oversized value), or the USDC price is 0 (pre-existing: also freezes pUSDC debtors). The message prints `shareState` |
| `share:poke-stalled` | warn | stored value older than 3 h while the vault CAN answer | the poking host (op1) is down, out of gas, or its fee cap is below the network fee: check `grant-host-status.sh`, op1's journal (`share:poke-error`), the op1 AVAX balance; poke by hand if needed |
| `share:poke-refused` | warn | `poke()` simulation returned `false` in 3 consecutive rounds although the vault answered and the value is old; nothing is sent | read `shareState()` by hand; the wrapper refuses to store. Raised ONLY on the poking host (op1): it is the loop's own counter, op2 and the treasury host do not simulate; they see the same problem as `share:poke-stalled` after 3 h |
| `share:poke-error` | warn | the last poke attempt failed (revert, mined-but-reverted, wallet below `minGasWei`, simulation reverted, gas estimate absurd, signer mismatch, receipt not confirmed) | the message names the cause; retried every 300 s; cleared by a success or when nothing is due (only op1) |
| `share:state-unreadable`, `share:price-unreadable` | warn | the wrapper's views cannot be read (wrong address in the config, RPC trouble) | the watch is blind: check `oracleWrapper` in the host config |

A host with no `oracleWrapper` or no `shareCollateral` block raises none of these. `share:poke-stalled` is the cross-host check: op2 and the treasury host raise it when op1's pokes stop. The poke runs even while the executor is HALTED (a halted liquidator still keeps the fallback fresh); it runs only in `run`, never in `check`.

## Gas for the poke (op1 wallet)
A poke is expected to cost about 50-80k gas (40k measured against a mock vault on a local EVM; the live vault's `convertToAssets` adds its feed reads), about 24 per day. Cost per poke = gas x network fee: at 70k gas, about 0.00007 AVAX at 1 gwei, 0.0018 at 25 gwei, 0.007 AVAX at the 100 gwei cap; per day 0.002 / 0.042 / 0.17 AVAX. I did not read the current network fee (no RPC access here): measure it before relying on a number. Keep at least 0.1 AVAX on the op1 wallet on top of what liquidation needs (the existing `monitor.minOperatorGasWei` and `executor.minGasWei` floors are 0.04 AVAX). Balance check: the status script shows the wallet balance, or `cast balance <op1 address>` with the host's own RPC. The poke loop itself refuses below `poke.minGasWei` and raises `share:poke-error`.

## Rollback
* Oracle: one transaction setting the old oracle back. The new build accepts it (allow-list), so no host action is needed. A host still on the OLD build halts at the swap and recovers by itself once the old oracle is back (the cycle error is not sticky).
* Poke loop: set `shareCollateral.poke.enabled` to `false` on op1 (or delete the block) and restart: the host stops sending; the wrapper keeps the last stored value and the fallback expires 24 h after it. Monitoring stays on (it needs only the wrapper address and the block); to silence it too, remove `oracleWrapper`/`shareCollateral` from that host's config, which is only sensible after the oracle is rolled back. Disabling the poke on op1 without enabling it elsewhere is a decision to let the fallback lapse.
* Share route: set `liquidation.enabled` to `false` and restart; the seized pTokens already held stay in the operator wallet (kept collateral is not recycled by any code path; a human decides).
* Image: restore the old tag (`docker tag pilot-operator:pre-bp-share pilot-operator:local`, then `systemctl restart pilot`). **Not proven**: that tag swap, and the old image itself, have not been exercised.

## Provenance and what was not done
* The images on the hosts were built ON each Droplet (`bootstrap-droplet.sh` tars the local `operator/` tree and runs `docker build -t pilot-operator:local`); which commit or working tree each one came from is not recorded anywhere I could read, and the rebuild overwrites the tag. The new build includes the alert-sink patch because this branch is based on it. Whether the running hosts already carry that patch is unknown.
* Wrapper-fallback keeper verification (21 Nov): `npm test` 145 tests pass (124 before: 21 new in `test/poke.test.ts`), `tsc` for both tsconfigs clean. The poke transaction path was also run against the REAL wrapper bytecode (artifact of `feat/bp-dlmm-core-v2`) with a mock vault/market/base oracle on a local anvil WITHOUT a fork: not due when fresh, poke at exactly 3,700 s with receipt and stored-time check, no second tx, an upward move stored with the +2% cap, the real `poke()` simulating `false` inside 1 h, fallback and price-0 findings from the real `shareState()`. NOT verified: the live vault's gas, a mainnet or fork run, the Telegram path (channel is `log`), a real keystore signer sending a poke.
* No image was built: docker is not available in this environment, and a build also needs the network (npm registry, node:22-slim). Not built, not run.
* Verified offline: `npm test` (unit tests incl. an in-memory chain that runs the executor, monitor and keeper end to end). NOT run: `npm run test:fork` (needs anvil and an archive RPC), anything on mainnet, the real wrapper contract, the real `liquidateBorrow` against the new pToken (the fork rehearsal of the liquidation belongs to the contracts side).
* Existing-market code touched: `src/txkit.ts` (the 180 s stall timer of the send helper is now cleared once the wait settles; without it a test run stayed alive for 3 minutes; no behaviour change) and the text of the `oracle-zero:<pToken>` finding in `src/health.ts` (now says "guarded oracle or wrapper"). Nothing else on the pWAVAX/pUSDC paths changed.
* Expected noise once someone borrows against shares: the `market:unrecoverable-debt-incomplete` warning (their debt cannot be valued: no reference price for shares) and one keeper skip line per cycle in the journal. A dust transfer of the share pToken to any borrower makes that account alert-only (fails closed).
* Existing alert keys keep their names. New keys: `executor:share-*`, `acct:<account>:share-collateral`, `share:*` (table above).
